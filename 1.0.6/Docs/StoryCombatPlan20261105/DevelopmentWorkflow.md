# 三 Boss 战斗与多结局协作开发流程

日期：2026 年 11 月 5 日。状态：开发执行草案。本文中的新增接口、目录和奖励规则为拟定方案，不表示代码已经实现或已向成员派单。

目标是让召唤 Boss 组与骑士 Boss 组独立制作，并能接入同一套玩家、伤害、剧情选择、奖励、存档和结局流程。每组既能单独试玩自己的关卡，也能交给整合负责人串联验收。

配套剧情以[完整故事与关卡策划 v0.4 方案稿](StoryAndEndings_v04.md)为阅读入口。两组仅处理本关行为，最终可达选项与结局由统一流程判定；不将上一轮流程图中的纯计数示例直接当成已冻结规则。

## 一 本轮范围与需要冻结的决定

| 关卡 | Boss | 本轮责任 |
| --- | --- | --- |
| 第一关 | 缚魂者，召唤亡灵 | 召唤组新增 Boss、敌方亡灵、缚魂装置和专属场景；交出可供后续使用的友方亡灵资产与行为 |
| 第二关 | 缄默典狱长 | 沿用现有成果，由整合负责人接公共接口、剧情节点和前后关状态 |
| 第三关 | 封印圣骑士 | 骑士组新增 Boss、武器、动作、技能和专属场景；交出最终冲突的剧情挂点 |
| 全流程 | 关卡串联与三个结局 | 整合负责人维护公共系统、统一选择界面、奖励应用、存档、结局和正式构建 |

两组首先做可完成的战斗关。剧情正文可以晚于战斗制作，但事件编号、触发条件和选择后的行为必须先约定。

开工前由负责人锁定以下内容并写进同一份接口说明：

1. 共同基线提交、Unity 版本和目标平台。
2. 三个 Boss 的识别编号、顺序，以及每关的开始、胜利、停战、失败和离开条件。
3. 玩家基础操作和能力是否沿用现版；两组不能各做一套玩家控制。
4. 每个剧情节点的血量阈值、只触发一次的规则，以及选择后继续战斗还是直接停战。
5. 第一关装置扣除的是当前生命还是生命上限。现阶段仅“减少 30 生命”已由设计提出，具体计算方式仍需确认。
6. 奖励、跨关保留、死亡重试和结局条件的初版规则。

结局原型可先记录克制与强制选择，以及装置、救援等事实状态。此前讨论的计数门槛和第二、三关选项仍是草案，不应由任一 Boss 组自行定为全局结局规则。

## 二 共同基线与分支

本次检查到的 main 为 `520dbea`。正式开工时重新刷新远端，将负责人批准的同一个完整提交作为共同基线，记录在接口说明和每次交付中。

| 用途 | 建议分支 | 管理者 |
| --- | --- | --- |
| 公共接口制作 | `codex/combat-foundation` | 整合负责人 |
| 召唤 Boss | `codex/boss-summoner` | 召唤组 |
| 骑士 Boss | `codex/boss-knight` | 骑士组 |
| 收取与串联验收 | 沿用 `codex/team-submit` | 整合负责人 |
| 已通过的共同版本 | `main` | 管理者 |

这些是拟用的新开发分支，不覆盖现有 `program`、`art`、`planner` 中尚未收取的工作。组内若还有多名程序或美术成员，可从对应组分支再建个人分支，由组负责人先完成组内整合。

每人使用自己的完整工程目录。从共同基线建立干净工作区，先保留原有未提交内容；不得多人同时编辑同一个磁盘目录。使用实际项目目录 `1.0.6/`，不改写 `lixiang` 的历史归档，也不为此次开发擅自创建归档版本号。

两组优先同步已经通过验收的公共基线。尚未验收的另一组实验代码，不直接整条合入本组。需要提前对接的功能，以公共接口或明确挑选的提交交接。

## 三 文件归属与场景组织

以下路径相对 Unity 工程 `1.0.6/`，属于建议新增结构。继续遵循现有 Core、Player、Interaction、Knowledge、UI、Visuals 模块划分。

| 归属 | 建议目录或文件 |
| --- | --- |
| 公共逻辑 | `Assets/Scripts/Core/CombatShared/`、`Core/StoryChoices/`、`Core/RunProgress/` |
| 公共玩家与界面 | 现有 Player 模块、公共战斗 HUD、选择界面、奖励界面 |
| 召唤组逻辑 | `Assets/Scripts/Core/Bosses/Summoner/`、`Assets/Scripts/Visuals/Bosses/Summoner/` |
| 召唤组资源 | `Assets/Art/Bosses/Summoner/`、`Assets/Audio/Bosses/Summoner/` |
| 骑士组逻辑 | `Assets/Scripts/Core/Bosses/Knight/`、`Assets/Scripts/Visuals/Bosses/Knight/` |
| 骑士组资源 | `Assets/Art/Bosses/Knight/`、`Assets/Audio/Bosses/Knight/` |
| 分组测试场景 | `Assets/Scenes/BossTests/Summoner_Test.unity`、`Knight_Test.unity` |
| 公共测试入口 | `Assets/Scenes/BossTests/CombatIntegration_Test.unity` |
| 对接文档 | `Docs/CombatCollaboration/`，下设 Shared、Summoner、Knight |

每组交付两个独立 Prefab：Boss 和 Arena。Arena 包含环境与位置锚点，不在里面再塞入正式玩家、EventSystem、公共 HUD 或存档管理器。单组测试场景引用同一套公共玩家和测试入口，组内临时调试物体须明确隔离。

位置统一按米制作，地面基准 Y=0。Arena 根物体为局部原点，交付用根缩放为 1；玩家出生点、Boss 出生点、入口、出口、剧情镜头位置均用具名子物体提供。运行位置由整合入口决定，不在组内脚本里写死世界坐标。

模型接入前统一朝向、比例、骨骼、Root Motion 使用方式、受击部位和武器挂点。动画事件可以驱动声音与特效，实际伤害由统一战斗时序控制，避免帧率或动画播放速度改变伤害次数。

公共文件只有整合负责人维护，包括玩家、输入绑定、通用 HUD、剧情选择、奖励、存档、主菜单、正式 Build Settings，以及公共 Layer、Tag 和项目设置。组内需要改公共内容时，提交需求、调用场景和最小复现，不直接复制出另一套系统。

资源必须保留原有 `.meta`；新资源使用独立 GUID。禁止把别组资源连同 `.meta` 改名复制成第二份。共享资源放公共目录，由负责人统一收取，不要求每组各交一份字体、玩家和输入资源。

## 四 公共接口先做一次占位联调

现有 `PlayerCombat`、`BossCombatHUD` 和部分战斗行为直接依赖 `BossEncounter`；现有 `BossEncounter.Begin()` 还要求典狱长专属场地与技能引用。仅新增两份模型和配置，不能自动得到三 Boss 支持。

由整合负责人先进行最小范围适配：保留原典狱长逻辑，通过适配层接入公共契约；将玩家攻击、伤害接收、HUD 数据和暂停逻辑接到统一入口。两组可以同时制作模型、白盒场景和技能设计，但在接口验收前不各自修改公共战斗底层。

下表是接口职责草案。实际类型与方法名由公共接口提交统一发布，两组按发布版本接入。

| 契约 | 提供什么 | 由谁实现 |
| --- | --- | --- |
| `IEncounterRuntime` | 开始、暂停、恢复、重试、结束、清理，以及当前战斗状态 | 公共层定义；各 Boss 控制器接入 |
| `IDamageable` | 统一受击入口、存活状态、阵营、命中结果 | Boss、召唤物、可破坏装置；玩家由公共层适配 |
| Boss 状态数据 | Boss ID、显示名、当前/最大生命、阶段、是否可受伤 | 各组提供；公共 HUD 读取 |
| `StoryBeatRequest` | 请求一个血量剧情或战后选择节点 | 各组发出；公共剧情系统展示 |
| `ChoiceResolution` | 确认选择，返回继续、换阶段、停战、结算等动作 | 公共系统返回；各组执行本关动作 |
| `EncounterResult` | 胜利、失败、停战、退出，和本关完成情况 | 各组发出；公共流程决定下一步 |
| `RunProgress` | 已提交选择、装备、永久标记、当前关卡和检查点 | 公共层统一维护 |

伤害请求至少携带来源、目标、阵营、伤害值、类型和是否允许格挡等信息。亡灵增援打骑士、玩家打亡灵、Boss 打玩家均走统一伤害入口；不得通过直接改另一组的生命字段来造成伤害。友军误伤、敌方召唤物是否可吞印等规则写入公共配置。

占位联调必须用同一个玩家和 HUD 依次启动一个典狱长适配器、一个召唤占位 Boss、一个骑士占位 Boss，跑通攻击、受击、剧情请求、选择返回、胜负、重试和退出。三者能用同一入口运行后，再冻结接口初版。

## 五 剧情触发与选择的统一流程

每个节点至少登记：

- `bossId`：例如 `summoner`、`warden`、`knight`。
- `beatId`：完整且唯一的节点编号，例如 `summoner.device_disposition`。
- 触发方式：血量跨越阈值，或战斗结束。第一关装置处置仍按战胜后发生；血量对白可以是另一个节点。
- `threshold`：需要时填写生命比例；阈值可配置，不在多个脚本中重复写死。
- `choiceId`：稳定的选项编号，不以界面中文台词作为程序判断条件。
- 前置与结果：需要的已完成事件、奖励 ID、装备状态、剧情标记和选择后战斗动作。
- 提交时机：即时、关卡完成或检查点提交；同一节点不能各组自行选择不同语义。

统一运行顺序如下：

1. 在伤害结算入口检测是否首次跨过剧情阈值，先于死亡和普通阶段切换处理。需要强制出现的节点不能被一次高伤害跳过；同次跨过多个节点时按配置顺序处理。
2. 进入剧情锁定状态，立即停止玩家与 Boss 的战斗行为。清除或停用未结算的攻击、敌方与友方召唤攻击、飞弹、持续伤害、回血和技能计时；清理不能再触发命中。
3. 公共系统处理玩家运动、输入、鼠标、声音、字幕和界面。不能只暂停 Boss，却让玩家下落、亡灵继续攻击或奖励持续回血。
4. 使用当前绑定显示提示。选择界面打开后保持不受伤；长按攻击键或连续点击不能穿透界面。
5. 玩家确认后，将选择、奖励和标记作为一次事务记录，再通知本关继续战斗、切换阶段、停战或结束。重复事件和存档恢复不能二次发奖。
6. 恢复前等待操作键释放，处理角色安全站位。暂停或失焦不能绕过尚未完成的剧情锁定。

一个节点有“未触发、待确认、已提交”三个持久状态。恢复到待确认节点时重新显示选择，不直接放玩家回战斗。正常流程不允许任意重开已提交选择刷奖励。

## 六 奖励 跨关继承与重试

选择奖励由各组提供定义和资源，公共奖励系统统一应用。组内脚本只申请奖励 ID，不各自修改玩家基础生命、攻击力或存档。

第一关的明确交接项是：

| 选择 | 需要传给后续关卡的状态 |
| --- | --- |
| 封印装置 | 记录封印选择；不生成受控亡灵援军；更新装置与相关亡灵表现 |
| 携带装置 | 发放装置；记录控制亡灵；启用友方召唤；按批准规则应用减少 30 生命的代价 |

装置只能被发放一次。若允许后续解除或摧毁，必须定义撤销增援、移除代价、更新结局事实标记的行为；历史上携带过装置的记录仍保留，不能用卸装备抹掉全部剧情后果。

敌方亡灵和友方增援应拆出公共行为或独立资源。召唤组负责把友方版本交给公共系统；骑士组通过公共阵营和伤害接口支持它，不引用召唤组的私有控制器。

建议将关卡开始作为完整重试点：保留此前关卡已经提交的选择与装备，撤销本次失败尝试中新产生的未提交奖励、临时召唤物和剧情节点状态。血量剧情需要中途保存时，由统一检查点同时保存关卡状态与选择结果，不能只回滚其中一半。

单组调试入口提供两种正式配置：无亡灵援军，以及携带装置并有援军及生命代价。骑士组从早期就用两种配置验收，不能等最终串联时才第一次遇到友方亡灵。

## 七 两组各自的开发步骤

### 召唤 Boss 组

1. 白盒验证场地、召唤位置、追踪路径、攻击预警和玩家可躲避空间。
2. 先接公共伤害与生命周期，让占位 Boss 和一种亡灵能完整战斗、暂停、死亡与重试。
3. 配置召唤数量上限、召唤间隔、存活条件、清理规则及性能预算；避免无限累积实体。
4. 接入血量剧情请求和战后的装置选择。Boss 战中对白与战后选择使用不同节点编号。
5. 交付友方亡灵版本，验证跨关伤害、跟随、寻路、目标选择、死亡和退出清理。
6. 替换正式模型、动画、材质、音效和特效，再完整复验，不直接沿用占位结果。

### 骑士 Boss 组

1. 先确定模型比例、武器、攻击范围、场地净空和镜头距离，再制作正式动作。
2. 白盒实现移动、防御、攻击预警、命中和收招。阶段切换与特效由数据驱动。
3. 接入公共伤害、HUD、暂停、失败、重试和退出；保证玩家原有攻击、防御与吞印规则一致。
4. 在批准的血量点发出剧情请求；按返回结果继续战斗、切换阶段或停战，不自行计算全游戏结局。
5. 用无增援和有增援两种状态测试。支持多目标受击，并写清骑士如何选择攻击玩家或友军。
6. 替换正式美术后复验近战距离、武器穿墙、碰撞、掉出场地及动画与伤害是否一致。

两组都应先完成一条可开始、可胜负、可重试的完整战斗，再增加技能与装饰。每个正式技能先约定预警、有效范围、伤害时刻、冷却和可反制方式。

### 本轮统一事件与选项编号草案

| 节点 ID | 触发 | 选项 ID | 公共层需要记录 |
| --- | --- | --- | --- |
| `summoner.low_health_dialogue` | 首次跨过批准的血量阈值 | 纯对白，无结局投票 | 已触发、对白恢复状态 |
| `summoner.device_disposition` | 战胜缚魂者 | `seal_device` / `carry_device` | 一次性选择、装置状态、增援、生命代价、倾向记录 |
| `warden.evacuation_priority` | 首次跨过批准的血量阈值 | `protect_evacuation` / `seize_supply` | 选择、后续战斗动作、救援实际完成、担保、奖励 |
| `knight.final_decision` | 首次跨过批准的血量阈值 | `cooperate_rescue` / `accept_seal` / `dominate_core` | 事实条件、已开放行动、最终决定和该行动实际完成 |

最终节点按可达条件显示选项，不要求每条路线都同时显示三个可选按钮。具体事实门槛以策划冻结后的唯一判定表为准。所有结局都在对应收尾行为完成并安全提交后出现，不能仅点选按钮就标记通关。

## 八 共同里程碑与对接门槛

以下是依赖顺序，不虚构成员工时或新的交付日期。负责人按实际人数和剩余时间填写日期。原比赛资料的截止为 11 月 7 日 22 时；三 Boss 与三结局是新增范围，是否纳入当次交付需由负责人评估，不能把本流程视为两天内全部完成的承诺。

| 阶段 | 召唤组 | 骑士组 | 公共整合 | 通过门槛 |
| --- | --- | --- | --- | --- |
| M0 范围与接口 | 交技能、装置与亡灵需求 | 交武器、阶段和剧情需求 | 锁基线、编号、文件归属 | 两组按同一份约定开工 |
| M1 占位接线 | Boss 与亡灵占位 | 骑士占位 | 完成公共适配和三入口测试 | 同一玩家能打三种占位入口 |
| M2 各关可玩 | 完整召唤战斗闭环 | 完整骑士战斗闭环 | 保持典狱长回归通过 | 各关可胜、可败、可重试 |
| M3 跨组联调 | 交友方亡灵与装置结果 | 接带援军与不带援军配置 | 串联奖励和两关状态 | 第一关选择能真实改变骑士战 |
| M4 剧情与结局 | 正式装置选择 | 正式血量节点 | 接典狱长节点、存档和结局 | 三关选择与结局能复现 |
| M5 美术与性能 | 正式模型、召唤特效 | 正式模型、动作和场景 | 统一声音、画质和构建 | 无丢引用、阻塞或性能失控 |
| M6 发布验收 | 修本组阻塞 | 修本组阻塞 | 完整独立包与第二设备复验 | 从正常入口可完成三条结局路线 |

M1 与 M3 必须实际运行，不能仅凭字段名称一致判断对接成功。每次联调记录共同基线、两组采用的提交、公共接口版本和实际结果。

## 九 每次交付与收取流程

每组至少交付：可运行测试场景、Boss 与 Arena Prefab、配置、脚本、动画和配套资源、完整 `.meta`、资源来源说明，以及一份交接记录。交接记录统一写：

1. 从哪个共同基线开发，本次有哪些独立提交，依赖哪个接口版本。
2. 入口场景与启动步骤，玩家及公共资源引用从哪里来。
3. 模型比例、Root Motion、碰撞、Layer/Tag 需求和寻路数据需求。
4. 技能参数、血量阈值、事件与选项编号、奖励 ID、选择后的动作。
5. 已跑的用例、实际结果、截图或视频，以及未验证项和已知问题。
6. 哪些公共文件需要负责人修改；列出原因，不夹带未经收取的项目设置覆盖。

每组先编译并检查 Console，确认没有缺失引用、重复 GUID 或缓存入库，再使用 Conventional Commits 提交并普通推送到自己的组分支。保持模型与 `.meta`、包锁文件和项目设置的完整性；大型资源按对应目录的 LFS 规则上传。不提交 Library、Temp、Logs、Builds、UserSettings 和本机 IDE 缓存。

整合负责人收取顺序：

1. 刷新远端，在隔离工作区检查变更与依赖。
2. 先收公共接口，再收单组完整且独立的提交；按提交依赖顺序进入 `codex/team-submit`。
3. 先做单关冒烟，再做召唤物跨关、奖励、剧情与存档联调，最后回归典狱长。
4. 冲突由对应文件负责人处理。遇到场景或 Prefab 冲突，先确认正确引用和装配结果，不直接整份覆盖。
5. 管理者验收后进入 main，再让两组同步新的共同基线。失败项留在收取分支修复，不强推、不把整个个人实验分支无差别合入。

不额外要求日报或 PR。接口变更、阻塞和交付需要记录清楚；接口破坏性改动由公共维护者发出明确变更说明，先给兼容方案与调用示例，再安排两组一起升级。

## 十 验收清单

| 范围 | 必测项目 |
| --- | --- |
| 基础战斗 | 玩家攻击/格挡/吞印、Boss 受伤、技能预警、胜负、重试、退出再进 |
| 血量节点 | 一次大伤害跨阈值、同帧多个命中、回血后再次跨越、攻击中触发；必要剧情不跳过且不重复 |
| 剧情安全 | 飞弹、持续伤害、友方与敌方亡灵、玩家重力、回血和计时同步停止；恢复不补算暂停期间伤害 |
| 选择提交 | 连点只提交一次；确认前退出、确认后读档、掉线式关闭程序后恢复不重复发奖、不丢关卡状态 |
| 装置 | 封印路线没有受控援军；携带路线增援有效且减血只应用一次；跨关、重试和读档结果一致 |
| 友方亡灵 | 正确阵营、不误伤玩家、不无限生成、不堵通关路线；能攻击骑士，离开场景后无残留 |
| 场景 | 出生点安全，武器与飞弹尊重墙体，角色不穿柱、不掉出边界；只有一个正式玩家和公共 UI |
| 既有内容 | 典狱长三水晶、减伤回血、全破僵直，以及旧剧情和菜单入口均未回退 |
| 结局 | 三条明确的选择记录分别走到对应结局；混合选择、已改变的装置状态及重试按同一判定表处理 |
| 独立包 | 指定平台正常启动、中文与声音正常、无需源码目录；真实设备记录分辨率、画质、帧时间和高峰实体数 |

同帧死亡与剧情触发的优先顺序必须由公共层固定，并覆盖玩家死亡与 Boss 致死两种情况。失败本身不计为强制或坏选择。

正式发布门槛是没有编译错误、主线阻塞、永久失去输入、存档或奖励重复、必要剧情被跳过，以及资源缺失。自动化检查不能替代完整人工战斗与首次体验；未运行的项目如实标注。
